psi6 0.4.0 桌面设计系统实施方案
目标：从“颜色主题”升级为“可组合、可扩展、可验证的桌面设计系统”。
这次不建议把工作限定在给现有控件补几条 QSS。更合理的做法是为 psi6 建立一套统一的设计基础，并提供两条视觉路线：
- Modern：通用现代风格——适用于普通桌面应用、设置页、表单、数据查看和日常生产力工具。
- Compact：专业工具紧凑风格——适用于开发工具、ETL、RPA、数据处理和多面板工作台。
两条路线共享同一套语义化设计 token、主题机制和交互规范，只在密度、控件尺寸、表面层级和部分视觉细节上有所区别。这样可以避免维护两套互不兼容的 UI 系统。
1. 0.4.0 的产品边界与设计原则
结合 psi6 当前的定位——Agent 优先的桌面开发框架——设计系统需要让编码 Agent 能够通过明确的规则创建一致的界面，而不是每次临时决定圆角、间距、颜色和控件行为。
设计原则	具体要求
语义优先	使用 surface、text_primary、border_subtle 等语义，不让控件依赖具体色值
风格与色彩分离	Modern / Compact 不等于 Light / Dark
统一状态	默认、悬停、按下、焦点、禁用、错误、选中都有明确规则
原生行为优先	保留 Qt 的键盘、焦点、可访问性和平台行为，避免无意义地重绘一切
逐步覆盖	先覆盖 psi6 自有控件和明确支持的控件，再逐步扩展 Qt 复杂控件
Python 原生配置	主题继续用 .py 定义，不引入 YAML、JSON、TOML 作为主题存储格式
Agent 可验证	有组件预览、主题诊断、自动化测试和清晰的使用文档
业务 UI 不入侵	psi6 提供设计基础设施，不内置 ETL 节点、打包向导等业务专用组件
版本目标： 0.4.0 建立完整的设计系统基础，完成一套可用于生产的参考实现和第二套紧凑变体；不要求在一个版本内完整复刻 Fluent、Material 或 macOS 全部设计语言。

2.2 第一版设计基准
以下数值可以作为 0.4.0 的初始设计基准，而不是不可修改的硬编码常量。最终应通过 psi6 kit 的组件预览和实际窗口验证。
设计属性	Modern	Compact
基础间距单位	4 px	4 px
常规控件高度	36 px	30 px
小型控件高度	28 px	24 px
主要输入框高度	36 px	30 px
圆角	6–8 px	4–6 px
面板内边距	16 px	10 px
常规组件间距	8–12 px	4–8 px
边框	轻量、克制	清晰、精确
阴影	浮层适量使用	默认少用
表格行高	32–36 px	26–30 px
图标尺寸	16–20 px	14–16 px
注意：
- 上述尺寸是初始逻辑像素（DIP）目标，不是物理屏幕像素。
- Compact 不意味着缩小所有可点击区域。小图标按钮应有足够的可点击区域，键盘操作仍需完整。
- 不应让每一个面板都变成圆角卡片。应用根背景、嵌套面板、输入框和浮层需要有不同的视觉层级。
- 不应依赖阴影来表达所有层次，边框、背景差异、留白和布局同样重要。
2.3 色彩与状态规范
继续支持 Light、Dark、Auto，但颜色应由语义 token 表达，而非让每个控件自行推导。
语义组	必须覆盖的角色
背景	window_bg、surface、surface_alt、surface_elevated
文本	text_primary、text_secondary、text_disabled、text_on_accent
边框	border、border_subtle、border_focus
强调色	accent、accent_hover、accent_pressed
选择	selection_bg、selection_text
状态	success、warning、danger、info 及相应的背景色
焦点	focus_ring、focus_ring_width
控件状态	hover、pressed、checked、selected、disabled、invalid
建议的状态规则：
- Hover：提供可感知但不过度突出的变化。
- Pressed：与 hover 明确区分，不仅仅是鼠标指针变化。
- Focus：键盘导航时必须有清晰的焦点指示；不能因为追求极简而移除。
- Disabled：同时改变视觉与交互行为，不单纯依靠降低透明度。
- Invalid：标识错误字段，配合文本说明，而不只使用红色边框。
- Selected：表格、列表、树视图、标签和可切换按钮应有一致的选中语义。
- Loading：异步操作要能表达处理中状态，并避免重复触发不允许并发的操作。
颜色对比度诊断继续沿用现有的 contrast_notes(app.tokens) 思路。诊断默认不应阻止主题加载，但可在测试或检查命令中用于发现问题。
3. Python 主题 API 设计
当前 psi6 已有 Theme、Tokens 和 contrast_notes，0.4.0 应优先演进这些能力，而不是另起一个并行主题框架。
建议的使用体验如下。这里是目标 API 草案，不是对现有实现的描述；正式合并前需要核对 src/psi6/api.py、现有 Theme 实现和兼容性约束。
3.1 应用级配置
from psi6 import App, DesktopWindow, Themeclass MyTheme(Theme):    name = "my_theme"    base = "light"    # 设计路线与密度    style = "modern"  # modern | compact    density = "comfortable"  # comfortable | compact    # 应用的品牌强调色    color_primary = "#4F46E5"    # 少量覆盖；其余 token 使用设计系统默认值    radius = 8app = App("demo", theme=MyTheme)window = DesktopWindow(title="My Application")raise SystemExit(app.run(window))



这里建议不要同时引入 style 和 density 两个含义重叠的复杂配置系统。一个明确的分工是：
- style 选择组件视觉规则，例如 modern 或 compact。
- density 控制控件尺寸与间距，例如 comfortable、standard、compact。
- base 继续控制浅色或深色的基础配色。
- 用户定义的 token 负责品牌色和局部视觉覆盖。
不过，若 style="compact" 已完整定义默认密度，也可以让 density 默认为 None，继承风格的默认值，避免两项配置冲突。建议正式 API 采用这种继承策略。
3.2 扩展 Tokens
建议把 token 分成三类，而不是让 Tokens 变成所有 UI 配置的杂物箱。
A. Color Tokens
语义色、背景层级、边框、文本、强调色、状态色、选择色。


B. Metric Tokens
基础间距、控件高度、图标尺寸、边框宽度、圆角、焦点环宽度。


C. Typography Tokens
字体族、正文字号、辅助文字、标题字号、字重、行高。


目标结构示例：
# 示意结构：正式实现可根据现有 Tokens 设计调整。from dataclasses import dataclass@dataclass(frozen=True)class PaletteTokens:    window_bg: str    surface: str    surface_alt: str    surface_elevated: str    text_primary: str    text_secondary: str    border: str    border_subtle: str    accent: str    accent_hover: str    accent_pressed: str    focus_ring: str    danger: str@dataclass(frozen=True)class MetricTokens:    spacing_unit: int    control_height: int    control_height_small: int    radius: int    border_width: int    focus_ring_width: int



这个例子是概念模型，不意味着应立即把这些类全部公开。实际实现时有两种选择：
1. 保留现有扁平 Tokens，逐步增加字段。兼容性较好，适合 0.4.0。
2. 在内部引入分组对象，如 tokens.colors、tokens.metrics、tokens.typography，并为旧字段提供兼容层。
建议：优先选择第二种内部结构、第一种公开兼容策略。 即内部结构清晰，外部 API 尽量稳定。如果现有 Tokens 字段已经成为公开契约，不应在同一版本里无必要地全部改名。
3.3 Python 文件主题
继续支持 .py 主题，不引入 JSON/YAML/TOML 存储。
建议支持两种方式：
- 类定义：适用于代码仓库中的主题，类型检查更容易。
- Python 模块或包：适用于复用主题和覆盖同目录资源，例如 icons/search.svg。
推荐规则：
- 默认值由框架提供。
- 主题只覆盖明确支持的字段。
- 未知字段应在加载时报告错误。
- token 值应进行类型和范围校验。
- 主题模块不应因当前工作目录变化而丢失资源定位。
- 自定义主题代码属于可执行 Python 代码，只加载可信来源；不应把它描述为安全沙箱。
3.4 主题运行时行为
需要明确以下契约：
1. base="light" 或 base="dark" 确定配色基底。
2. 风格与密度选择视觉规则和尺寸。
3. 自定义 token 覆盖默认值。
4. 应用启动时解析成不可变的有效 token 集。
5. 控件从有效 token 和状态规则获取样式。
6. 如果支持运行时切换主题，已存在的控件也必须更新，而非只影响之后创建的控件。
运行时切换应纳入设计，但是否作为 0.4.0 的稳定公开 API，要根据现有实现和测试范围决定。无论如何，不能让控件直接缓存旧色值，造成主题更新不完整。
4. 模块边界与建议目录结构
0.4.0 的目标不是把所有样式都写进一个大模块，而是让 Agent 能清楚地知道：在哪里定义主题、在哪里实现控件、在哪里测试视觉效果。
建议结构如下，具体路径应先与现有仓库对照，避免机械搬迁：

src/psi6/
├── api.py
├── theme/
│   ├── __init__.py
│   ├── theme.py              # 用户主题定义与覆盖
│   ├── tokens.py             # token 定义与校验
│   ├── resolver.py           # 默认值、风格、用户覆盖合并
│   ├── palette.py            # Light / Dark 语义色
│   ├── metrics.py            # 尺寸、间距、圆角
│   ├── typography.py         # 字体与字号
│   └── diagnostics.py        # 对比度、字段与配置诊断
├── styles/
│   ├── __init__.py
│   ├── base.py               # 风格接口及通用规则
│   ├── modern.py             # Modern 参考风格
│   ├── compact.py            # Compact 参考风格
│   └── states.py             # 通用控件状态规则
├── ui/
│   ├── ...                   # 现有公开控件
│   └── ...                   # 仅在需要时新增通用控件
└── _internal/
    ├── ...                   # Qt 样式适配、资源和运行时内部实现



这只是逻辑边界，不要求完全照搬目录。如果现有仓库已经有成熟的 theme.py、ui 或内部样式模块，应优先在现有结构内整理。
各模块的职责
模块	负责	不负责
theme.py	用户主题声明、覆盖入口	直接为每个控件拼接 QSS
tokens.py	token 类型、字段、默认值和校验	控件的具体绘制
resolver.py	组合基础配色、风格、密度和用户覆盖	业务页面逻辑

公开 API 原则： psi6.api 继续作为稳定入口。内部解析器、Qt 适配器和 QSS 生成器不应直接变成公共 API。只有确实需要用户扩展的概念才进入公开导出名单。
5. 控件覆盖清单
不要试图在 0.4.0 一次性重写 PySide6 的所有控件。应先建立一个有优先级的支持矩阵。
P0 — 第一批：主题一致性的基础控件
- 按钮：主按钮、次按钮、危险按钮、图标按钮、切换按钮
- 输入：单行文本、多行文本、数字输入、组合框
- 选择：复选框、单选框、开关、下拉选择
- 反馈：标签、提示、进度条、状态提示
- 容器：面板、分组框、分隔线、卡片
- 窗口：DesktopWindow、TitleBar、菜单、基础对话框



P1 — 第二批：专业桌面工具的关键控件
- 表格与表头、选中行、排序状态
- 树视图、列表视图、行悬停与选中
- 标签页、工具栏、状态栏、侧边导航
- 可折叠区域、分割器、停靠面板（如现有架构支持）
- 进度与任务状态展示
- 统一的错误、空数据、加载中状态



P2 — 有明确需求再支持
- 高级图表、复杂富文本编辑器
- 第三方 Qt 控件
- 完全自定义绘制的特殊组件
- 跨平台差异明显的系统原生控件
对这些控件先定义兼容边界和适配指南，不承诺所有第三方控件自动主题化。



每个控件必须覆盖的状态
状态	必须验证的行为
Default	基础样式与文本清晰
Hover	指针悬停时有合适反馈
Pressed	按下时反馈明确
Focus	键盘聚焦时可识别
Disabled	不可交互且视觉清晰
Selected / Checked	选中状态一致
Invalid	校验错误可识别，且有辅助说明
Loading	耗时操作有反馈，不出现重复触发
Light / Dark	两种配色都可用
Modern / Compact	两种风格规则都一致
不要求每个控件都支持每个状态。例如纯展示标签不需要 pressed，但需要在测试清单里明确标注“不适用”，而不是默默遗漏。
6. 桌面 UI/UX 规范
设计系统不应该只控制颜色和 QSS。它还需要规定应用的常见交互行为。
6.1 窗口与导航
- 默认保留 Qt 原生标题栏；自绘标题栏仍通过 frameless=True 显式启用。
- 窗口大小、位置、多显示器、缩放和关闭行为由现有窗口 API 管理，不由视觉风格任意改变。
- 主导航、工具栏、内容区、状态栏应有清楚的职责划分。
- Modern 可以采用较宽松的导航和留白；Compact 可以缩小面板内边距，但不应隐藏关键功能。
- 不要求所有应用采用固定布局；设计系统提供建议模式，而不是业务页面生成器。
6.2 对话框与反馈
- 只有需要用户决策的操作才使用确认对话框，避免每个动作都弹窗。
- 对话框按钮顺序、默认按钮、取消行为应遵循平台习惯。
- 错误反馈必须包含可理解的信息和可执行的下一步，避免只显示“失败”。
- 不可逆操作需要明确的危险操作样式与语义。
- 加载、空状态、成功、警告和失败应形成统一的反馈模式。
6.3 后台任务与 UI 生命周期
psi6 已有 TaskRunner、TaskHandle，设计系统应给出与其一致的任务 UI 约定：
- UI 负责展示状态和接收用户操作；耗时工作交给 TaskRunner。
- 任务开始、进度、日志、成功、失败和取消应有统一的视觉反馈。
- cancel() 代表发出取消请求，不能立即假定任务已经终止。
- 关闭窗口不自动取消任务的既有语义不能被视觉层悄悄改变。
- 应用退出时的任务处理与现有 runtime 契约保持一致。
- 回调更新 UI 时必须遵守 Qt 线程规则。
6.4 键盘、焦点与可访问性
- 所有关键操作都应支持键盘访问。
- 焦点顺序要符合视觉顺序和任务流程。
- 快捷键不能随意覆盖系统或平台常见快捷键。
- 表单校验错误不能仅通过颜色表达。
- 文本缩放、系统 DPI、字体替换和高对比度环境需要有基本验证。
- 自定义绘制控件必须明确如何提供焦点、键盘操作和可访问性信息。
6.5 图标与资源
- 使用一致的图标尺寸、对齐、线条重量和明暗适配规则。
- 优先使用明确的图标资源约定，而不是依赖任意的当前工作目录。
- 主题资源覆盖机制应沿用已有能力，保证安装后和打包后仍可定位。
- 不要求所有应用都使用同一套图标；但应提供推荐尺寸、命名和浅色/深色适配规范。
7. 组件预览与主题诊断
现有 python -m psi6 kit 是这次升级的重要基础。建议将它发展成设计系统的可视化验证入口，而不是另做一套独立的主题编辑器。









组件目录
按按钮、输入、选择、导航、数据展示、反馈和窗口分组，展示组件实际外观。











状态对照
同屏展示默认、悬停、按下、焦点、禁用、错误和选中状态，帮助 Agent 和开发者发现视觉不一致。











主题与风格切换
在 Modern / Compact 和 Light / Dark 之间切换，验证已有控件是否正确更新。



建议增加的诊断能力
可考虑在现有示例检查之外，增加一个专门的主题检查入口，例如：
python -m psi6.theme_check my_theme.py


这个命令只是建议的 CLI 形式，最终要根据当前项目的命令结构决定。
诊断至少应该检查：
- 未知 token、错误类型和非法取值。
- 必填语义 token 是否缺失。
- Light / Dark 配色是否完整。
- 关键文本与背景的对比度是否存在明显问题。
- 风格或密度配置是否无效。
- 主题引用的资源文件是否存在。
- 主题模块是否能在独立安装环境中正确加载。
建议将结果分为 error、warning 和 info。未知字段或无效值属于错误；对比度不足通常是警告。检查命令应提供稳定退出码，方便 Agent 自动修复。

8. 0.4.0 模块边界与公开 API 决策
当前 README 已将根包公开接口收敛到明确名单。因此这次应该优先扩展现有接口，而不是大量增加根包导出。
建议按下面的原则决策：
候选 API	建议
Theme、Tokens	继续作为稳定公开接口

psi6 0.4.0 — Cursor Agent 实施计划
项目背景
psi6 是面向编码 Agent 的轻量 PySide6 桌面框架。0.4.0 的目标是将当前以颜色为主的主题系统升级为完整的桌面设计系统。
本版本提供两条视觉路线：
- modern：通用现代桌面风格。
- compact：专业工具紧凑风格。
两条路线共享语义化设计 token、主题加载机制和交互规范。每条路线均需支持 Light / Dark 配色。
继续使用 Python .py 主题文件。不得引入 YAML、JSON、TOML 作为主题存储格式。
保持 psi6 的边界：提供运行时、通用桌面 UI、主题与设计基础设施，不引入业务专用页面、ETL 节点、打包向导或内置 Agent runtime。
全局约束
1. 先阅读现有实现和测试，不要根据 README 猜测内部结构。
2. 优先演进现有 Theme、Tokens、contrast_notes 和 psi6 kit。
3. 未经明确论证，不得批量重命名公开 API、移动所有模块或重写全部控件。
4. psi6.api 继续控制稳定公开导出；内部解析器、样式生成器和 Qt 适配器不得无故公开。
5. 不得为了视觉统一破坏 Qt 键盘、焦点、可访问性和平台原生行为。
6. 不得改变现有任务取消、关窗和应用退出语义。
7. 所有新增功能必须有测试、文档和示例。
8. 每项任务完成后运行相关测试，并报告变更文件、测试结果、已知限制和下一步建议。
9. 不得在未验证的情况下声称 Windows、macOS、Linux 全部通过。

12. 我对这次版本的最终建议
0.4.0 最重要的交付物，不是新增了多少个主题参数，而是形成三个可持续的能力：
1. 可组合的设计系统：Modern / Compact 与 Light / Dark 可以组合，颜色、尺寸、字体、状态有统一来源。
2. 真正可用的桌面交互规范：焦点、键盘、任务、错误反馈、窗口和复杂控件不再依赖 Agent 临时发挥。
3. 可验证的参考实现：通过组件预览、主题诊断和测试，让 Agent 能检查自己生成的界面是否符合 psi6 规范。
我建议先做任务 1 的仓库审计，再根据实际现状确定任务 2–7 的工作量。这样可以避免设计了一套漂亮的 API，却发现与现有 Qt 控件、主题机制或公开接口难以兼容。
